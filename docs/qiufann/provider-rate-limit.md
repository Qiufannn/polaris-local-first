# 第三方线路的 429 与请求暂缓

同一配置在真实私聊和群聊中交替成功、返回 `API 429 / Resource exhausted`，说明请求至少在部分时间被接受，不能仅凭错误文案认定模型名称配置错误或账户余额耗尽。中转站的账户限制、模型上游容量、RPM / TPM 与并发限制仍需站方按失败 request ID 核对。成功消费页没有失败记录也不能证明失败请求没有发出。

## 本次客户端保护

- 群聊现有实现允许成员通过互相点名继续接话；点名排队不等于一次 HTTP 请求失败后的自动重试，但会追加新的模型调用。
- 真实回复遇到 HTTP 429 时，携带限流标记返回请求调度器。该供应商随后在本机暂缓 60 秒；再次到期后仍返回 429 时增为 120 / 240 秒，最多 300 秒，成功回复后重置。此时间只用于本地退避，不是服务端额度恢复时间。
- 同一供应商 ID 的私聊、群聊、成员小窗和主动任务共用暂缓状态。其他供应商可继续使用，保护不会自动换模型、付费线路或账号。
- 暂缓中，尝试发送会显示剩余时间与「本次没有发送新请求」，不进入模型调用，不制作一条假的成员回复；时间到期也不会自行补跑。
- 保护是内存状态，重开应用会清空。不能取消已经在途的其他请求，也不能代替站方修复资源限制。
- 正常群聊接话机制没有被改成固定每人一句；本次没有新建角色、群或真实 API 试探请求。

## 调试边界

不索取凭据，不以循环发送、切换模型或充值作为默认排查方式。计费以各模型在供应商面板的实际规则为准，不能假设短请求一定便宜。

本地用假数据对比「供应商默认模型 + 空覆盖」与「另一个供应商默认模型 + 相同有效模型覆盖」的真实请求构造：当供应商其他字段与有效模型 ID 完全相同时，组装结果一致。该证据不能证明手机上两份配置和服务器路由也完全相同。

手机仍需观察一次实际 429 后，在暂缓期内是否显示本地提示、供应商端是否没有新增相应请求；本地和 CI 测试不能代替服务器日志或真实手机验收。
